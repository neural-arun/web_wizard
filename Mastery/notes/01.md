# Playright Theory.

### **Module A: Web Foundations**

#### **1. HTTP Fundamentals**
The backbone of web communication. Understanding HTTP allows you to intercept traffic and often bypass the UI entirely for faster data extraction.
* **Core Methods:**
    * `GET`: Requests data from a specified resource (e.g., loading a webpage).
    * `POST`: Submits data to be processed (e.g., submitting a login form).
    * `PUT`/`PATCH`: Updates existing data.
    * `DELETE`: Removes data.
* **Headers:** Key-value pairs providing metadata about the request/response. 
    * *Crucial for scraping:* `User-Agent` (identifies your browser/bot), `Authorization` (passes tokens), `Accept` (expected data format), and `Cookie` (session management).
* **Status Codes:**
    * **2xx (Success):** `200 OK` (Perfect), `201 Created`.
    * **3xx (Redirection):** `301 Moved Permanently`, `302 Found`.
    * **4xx (Client Error):** `401 Unauthorized`, `403 Forbidden` (often hits anti-bot systems), `404 Not Found`, `429 Too Many Requests` (rate limited).
    * **5xx (Server Error):** `500 Internal Server Error`, `502 Bad Gateway`, `503 Service Unavailable`.

#### **2. HTML / DOM / CSS Selectors**
This is how you locate and extract exactly what you need from the visual layer.
* **HTML (HyperText Markup Language):** The static, raw skeleton of a webpage sent from the server.
* **DOM (Document Object Model):** The live, interactive tree structure the browser builds from the HTML. *Note:* JavaScript dynamically modifies the DOM. When using Playwright, you are scraping the live DOM, not the static HTML.
* **CSS Selectors:** The syntax used to precisely target DOM elements.
    * `.classname` targets classes (e.g., `.product-price`).
    * `#idname` targets unique IDs (e.g., `#submit-button`).
    * `element` targets specific tags (e.g., `h1`, `a`, `div`).
    * `div > p` targets direct children.
    * `[attribute="value"]` targets specific attributes (e.g., `[data-testid="login-input"]` — **Pro-tip:** Always use data attributes when available for maximum reliability).

#### **3. Browser DevTools Quick Actions**
Your primary diagnostic tool for reverse-engineering websites before writing a single line of code.
* **Elements Tab:** Used to inspect the live DOM, identify class names, and test your CSS/XPath selectors by hitting `Ctrl+F` (or `Cmd+F`).
* **Network Tab:** The most critical tab for scaling operations. Used to monitor all HTTP traffic. Filter by `Fetch/XHR` to find the underlying JSON APIs powering the site. If you can query the API directly, you don't need to load the browser at all.
* **Console Tab:** A live JavaScript environment. Used to test DOM manipulation, print variables, and quickly prototype selector logic using `document.querySelector()`.

#### **4. Tool Ecosystem Comparison**
Understanding where Playwright sits in the ecosystem ensures you use the right leverage for the specific domain problem.

| Feature | Playwright | Selenium | Scrapy | Puppeteer |
| :--- | :--- | :--- | :--- | :--- |
| **Core Architecture** | Modern, bi-directional WebSocket connection. | Traditional HTTP WebDriver protocol (W3C). | Pure Python async HTTP framework. | Node.js library controlling Chrome via DevTools Protocol. |
| **JS Rendering** | **Yes.** Full browser execution. | **Yes.** Full browser execution. | **No.** Requires middleware (Splash/Playwright). | **Yes.** Full browser execution. |
| **Speed** | Fast. Auto-waits for elements to be actionable. | Slower. Prone to flakiness without explicit waits. | **Extremely Fast.** No browser overhead. | Fast, but effectively limited to Chromium. |
| **Best Used For** | Resilient end-to-end testing, modern SPA scraping, and bypassing complex bot protection. | Legacy enterprise systems, very niche browser support. | Large-scale, high-speed crawls of static or API-driven data. | Node.js developers focusing solely on Chrome automation. |
| **Language Support**| Python, TS/JS, Java, .NET | Python, Java, C#, Ruby, JS | Python only | JavaScript/TypeScript only |

# Module B

**Install & Setup (`playwright`, Playwright Python)**

0. Where this fits in the system  
`CI/container build → Python package + browser binaries → worker startup`  
`worker startup → healthcheck → job execution`

1. What is this  
This is the dependency and runtime provisioning layer. You study package install, browser binary install, version pinning, CI/container setup, and boot-time validation. In Python, the package is `playwright`; “Playwright Python” refers to the Python binding/docs, not a separate package name you usually install.

2. How to use this in real systems  
Practical example: bake Playwright and browser binaries into the worker image, then run a startup probe before taking jobs. This usually lives in CI, Docker build, and worker bootstrap code.

```bash
pip install playwright
python -m playwright install chromium
```

```python
async def startup_probe():
    from playwright.async_api import async_playwright
    async with async_playwright() as p:
        browser = await p.chromium.launch()
        await browser.close()
```

3. Why does it exist  
Browser automation needs two things: the Python client and compatible browser executables. Without this split, environments drift and runtime failures move from build time to production time.

4. What happens if you remove it  
You get `ModuleNotFoundError`, missing executable errors, CI-only failures, or runtime launch failures after deploy. System impact is broken workers, failed jobs, and non-reproducible environments across dev, CI, and prod.

5. When to use vs when not to use  
Use when:
- You run browser automation in local dev, CI, containers, or workers
- You need repeatable browser versions across environments

Avoid when:
- Plain HTTP/API calls are enough
- A managed browser platform already owns the browser runtime

6. Failure patterns & debugging signals  
- Symptom: `Executable doesn't exist` or launch failure; root cause: browser binaries not installed; debug: rerun `python -m playwright install`, verify image layer.
- Symptom: works locally, fails in CI; root cause: version drift; debug: pin package version and rebuild image.
- Symptom: slow cold starts; root cause: downloading browsers at runtime; debug: move install to build step.

**Sync vs Async API (`playwright.sync_api`, `playwright.async_api`)**

0. Where this fits in the system  
`job handler → execution model choice → sync or async Playwright calls`  
`execution model → worker throughput and integration style`

1. What is this  
This is the control model for how your code talks to the browser. You study sync vs async usage, event loop behavior, concurrency, integration with web servers/workers, and boundaries between blocking and non-blocking code.

2. How to use this in real systems  
Use `async_api` in queue workers, APIs, and agents because browser work is heavily I/O-bound. Use `sync_api` for tiny scripts and local utilities. This typically lives in worker code, service code, or internal automation tools.

```python
from playwright.async_api import async_playwright

async def run_job(job):
    async with async_playwright() as p:
        browser = await p.chromium.launch()
        page = await browser.new_page()
        await page.goto(job["url"])
        return await page.title()
```

3. Why does it exist  
Some systems want simple imperative scripts; others need concurrency and clean event-loop integration. One API style cannot optimize equally well for both.

4. What happens if you remove it  
If you force sync inside async services, worker throughput drops and request handlers block. If you force async everywhere, simple scripts become harder to read and onboard.

5. When to use vs when not to use  
Use when:
- `async_api` for web services, agents, task queues, and concurrent jobs
- `sync_api` for local scripts, one-off tools, and quick experiments

Avoid when:
- Mixing sync and async in the same call path without a clear boundary
- Using sync Playwright inside a high-concurrency async app

6. Failure patterns & debugging signals  
- Symptom: event loop errors or hanging tasks; root cause: async misuse; debug: verify every Playwright call is awaited.
- Symptom: low throughput under load; root cause: blocking sync calls in async worker; debug: profile worker concurrency and switch boundary to async.
- Symptom: hard-to-test glue code; root cause: unclear sync/async boundary; debug: isolate Playwright behind one service interface.

**`async_playwright()` Lifecycle**

0. Where this fits in the system  
`worker startup/job start → Playwright runtime boot → browser access`  
`job end/service shutdown → runtime teardown → resource cleanup`

1. What is this  
This is the root lifecycle manager for Playwright in async Python. You study startup, shutdown, transport ownership, reuse patterns, and how browser resources are created and cleaned up over time.

2. How to use this in real systems  
Use it as a startup/shutdown boundary. In long-running workers, start once and reuse; in short-lived jobs, use it per job. This usually lives in service bootstrap code or a browser service class.

```python
from playwright.async_api import async_playwright

class BrowserRuntime:
    async def start(self):
        self.pw = await async_playwright().start()
        self.browser = await self.pw.chromium.launch()

    async def stop(self):
        await self.browser.close()
        await self.pw.stop()
```

3. Why does it exist  
The browser connection needs a managed runtime and clean teardown. Without a clear owner, processes, sockets, temp files, and memory leak across jobs.

4. What happens if you remove it  
Browsers remain open, worker memory grows, temp resources accumulate, and jobs become unstable over time. In production, this shows up as zombie processes and degraded worker health.

5. When to use vs when not to use  
Use when:
- You need any async Playwright session
- You want explicit startup and cleanup ownership

Avoid when:
- Starting and stopping it repeatedly inside tiny inner loops
- Treating it as a short-lived helper for every click or query

6. Failure patterns & debugging signals  
- Symptom: hanging shutdown; root cause: runtime not stopped cleanly; debug: inspect worker shutdown hooks.
- Symptom: memory/process growth; root cause: leaked browsers or contexts; debug: count child processes and open handles.
- Symptom: “browser closed” mid-job; root cause: shared runtime torn down too early; debug: verify ownership boundaries.

```python
async def launch_for_job(p, job):
```

5. When to use vs when not to use  
Use when:

Avoid when:
- You control the runtime and only support one engine
- Speed is more valuable than compatibility breadth

6. Failure patterns & debugging signals  
- Symptom: test passes in Chromium, fails in WebKit; root cause: engine-specific behavior; debug: compare screenshots and trace by engine.
- Symptom: only Safari users report issues; root cause: no WebKit coverage; debug: add targeted WebKit jobs.
- Symptom: flaky visual differences; root cause: engine/rendering variance; debug: separate logic failures from layout differences.

**BrowserContext vs Page**

0. Where this fits in the system  
`browser process → BrowserContext (session boundary) → Page (tab/document)`  
`context config → page behavior → job result`

1. What is this  
`BrowserContext` is the isolated session; `Page` is a tab inside it. You study session isolation, storage state, cookies, permissions, viewport, auth reuse, tab management, and context-per-job design.

2. How to use this in real systems  
Use one fresh context per user/job and one or more pages inside it. This usually lives in the browser worker layer where auth, isolation, and artifact policy are enforced.

```python
async def run_tenant_job(browser, tenant):
    context = await browser.new_context(storage_state=tenant["state"])
    page = await context.new_page()
    await page.goto(tenant["dashboard"])
    data = await page.title()
    await context.close()
    return data
```

3. Why does it exist  
Systems need isolation between tenants, users, and jobs without paying for a full new browser process every time. Context gives a cheaper and cleaner session boundary.

4. What happens if you remove it  
Cookies and local storage leak across jobs, auth becomes flaky, permissions bleed between users, and recordings/emulation become harder to scope. This is a direct data isolation risk.

5. When to use vs when not to use  
Use when:
- You need per-user or per-job isolation
- You need session-level config like storage, geolocation, or video

Avoid when:
- You are writing a tiny single-page demo
- You do not need session separation or custom session config

6. Failure patterns & debugging signals  
- Symptom: wrong user appears logged in; root cause: shared context; debug: inspect cookies/storage state per job.
- Symptom: permissions or viewport seem inconsistent; root cause: context reuse across different jobs; debug: log context creation parameters.
- Symptom: videos/downloads missing; root cause: wrong ownership layer; debug: verify context settings and close order.

**Locators: CSS, XPath, text, role selectors**

0. Where this fits in the system  
`loaded page/frame → locator resolution → target element`  
`target element → action/assertion → state change`

1. What is this  
Locators are Playwright’s targeting layer for finding UI elements. You study semantic locators (`role`, `label`, `text`, `test id`), CSS, XPath, resilience, and how target selection affects long-term maintainability.

2. How to use this in real systems  
Prefer role, label, or text because they align with user-visible behavior. Use CSS when semantics are unavailable, and XPath only as a last resort. This typically lives in page-object code, worker logic, or agent tools.

```python
async def login(page, creds):
    await page.get_by_label("Email").fill(creds["email"])
    await page.get_by_label("Password").fill(creds["password"])
    await page.get_by_role("button", name="Sign in").click()
```

3. Why does it exist  
Raw DOM selectors are fragile because frontend structure changes often. Locators exist to make interactions stable, auto-waiting, and closer to real user intent.

4. What happens if you remove it  
You get brittle selectors, frequent “element not found” failures after harmless UI refactors, and higher maintenance cost. System reliability drops because automation is tied to markup shape, not behavior.

5. When to use vs when not to use  
Use when:
- Interacting with visible UI
- You can identify elements by role, label, text, or stable test id

Avoid when:
- Defaulting to XPath for everything
- Scraping static HTML when a browser is not needed

6. Failure patterns & debugging signals  
- Symptom: locator resolves multiple elements; root cause: selector too broad; debug: narrow by role name, text, or container.
- Symptom: element not found after redesign; root cause: DOM-based selector drift; debug: switch to semantic locator.
- Symptom: hidden wrong target clicked; root cause: ambiguous selector; debug: inspect locator count and visibility.

**Actions: click, fill, type, hover, dblclick**

0. Where this fits in the system  
`locator resolved → action dispatched → browser events/UI change`  
`UI change → network/app logic → next state`

1. What is this  
Actions are the browser interactions sent to elements. You study click behavior, form input strategy, hover-based menus, double-click flows, and the difference between setting final values and simulating keystrokes.

2. How to use this in real systems  
Use locator-based actions. Prefer `fill()` for normal forms, and use per-keystroke input only when the app reacts to each keypress. This usually lives in page actions, workflow orchestration, or browser-agent tools.

```python
search = page.get_by_label("Search")
await search.fill("playwright")
await page.get_by_role("button", name="Open menu").hover()
await page.locator(".row").dblclick()
```

3. Why does it exist  
Web apps respond through browser events, focus rules, and actionability checks. Actions exist so automation triggers the same UI pathways users trigger, instead of bypassing the app with DOM hacks.

4. What happens if you remove it  
Teams fall back to JavaScript shortcuts or direct DOM mutation, which bypass real UI behavior and create false positives. Observable issues include missed validations, wrong event order, and unstable flows.

5. When to use vs when not to use  
Use when:
- You need real UI behavior, focus handling, or click-driven logic
- You want Playwright’s actionability and retry behavior

Avoid when:
- You only need read-only extraction
- You use key-by-key typing for ordinary forms where `fill()` is cleaner

6. Failure patterns & debugging signals  
- Symptom: click timeout; root cause: element covered, disabled, or not actionable; debug: inspect visibility and overlays in trace/screenshot.
- Symptom: value appears but app logic does not react; root cause: wrong input method for that field; debug: test `fill()` vs key-driven entry.
- Symptom: hover menu never opens; root cause: wrong target or detached element; debug: pause and inspect DOM state before action.

**Navigation & Routing: `page.goto()`, `page.wait_for_load_state()`**

0. Where this fits in the system  
`job URL or click → navigation layer → new document/state`  
`new document/state → readiness signal → interaction phase`

1. What is this  
This is the document-transition layer. You study direct URL entry with `goto()`, page-level load milestones, popup/new-page readiness, and when document readiness is different from business readiness.

2. How to use this in real systems  
Use `goto()` to enter known pages and `wait_for_load_state()` for hard navigations, popups, or explicit page transitions. This usually lives in workflow orchestration code inside a worker or test runner.

```python
await page.goto(job["url"], wait_until="domcontentloaded")
async with page.expect_popup() as pop:
    await page.get_by_role("link", name="Open report").click()
report = await pop.value
await report.wait_for_load_state("load")
```

3. Why does it exist  
Page transitions are asynchronous and involve networking, parsing, and rendering. These APIs exist to prevent your next step from racing a document that is still changing.

4. What happens if you remove it  
You interact with half-loaded pages, miss popup readiness, and get random timeouts or missing elements. If you overuse load waits, you also slow the system with unnecessary blocking.

5. When to use vs when not to use  
Use when:
- You enter the app by URL
- You need readiness for a new tab, popup, or hard navigation

Avoid when:
- A specific UI signal is a better readiness check than page load
- Using `networkidle` as a generic “page is ready” rule

6. Failure patterns & debugging signals  
- Symptom: element not found right after `goto`; root cause: wrong readiness assumption; debug: wait for a meaningful locator instead of only load state.
- Symptom: popup object exists but page content is incomplete; root cause: interaction before popup load; debug: add `wait_for_load_state()` on popup.
- Symptom: slow jobs; root cause: excessive navigation waits; debug: measure time spent waiting versus actual UI readiness.

**Waits: explicit waits, `locator.wait_for()`, `page.wait_for_selector()`**

0. Where this fits in the system  
`action fired or navigation finished → synchronization layer → stable next step`  
`synchronization layer → lower flakiness → deterministic workflow`

1. What is this  
This is the timing-control layer. You study Playwright auto-waiting, explicit waits for real signals, `locator.wait_for()` as the modern pattern, and `page.wait_for_selector()` as older but still common code you may see.

2. How to use this in real systems  
First rely on Playwright’s built-in waiting. Add `locator.wait_for()` only when the appearance, disappearance, or attachment itself is the business signal. This typically lives in workflow logic and failure-recovery code.

```python
status = page.get_by_test_id("sync-status")
await status.wait_for(state="visible")
await page.get_by_role("button", name="Download").click()
```

3. Why does it exist  
The browser and frontend are asynchronous. Waits exist so you advance on real state changes instead of guessing with arbitrary delays.

4. What happens if you remove it  
People replace signal-based synchronization with `sleep()`, which creates slow fast-paths and flaky slow-paths. Observable effects are intermittent timeouts, duplicate retries, and unstable pipelines.

5. When to use vs when not to use  
Use when:
- Element state is the real gate for the next step
- You need to wait for visible, hidden, attached, or detached state

Avoid when:
- An action already auto-waits enough
- You reach for fixed sleeps instead of state-based synchronization

6. Failure patterns & debugging signals  
- Symptom: random timeout after click; root cause: missing post-action signal wait; debug: identify the real UI signal and wait for it.
- Symptom: slow jobs everywhere; root cause: blanket sleeps; debug: replace with locator-based waits and compare timing.
- Symptom: stale legacy code around `wait_for_selector`; root cause: old style sync logic; debug: migrate critical paths to locators.

**Tracing, Screenshots, PDFs, Video Recording**

0. Where this fits in the system  
`job execution → observability/artifact layer → stored evidence`  
`stored evidence → debugging, audit, replay, document output`

1. What is this  
These are execution artifacts around browser runs. You study traces, screenshots, video recording, and PDF generation so the system can explain what happened after a run completes or fails.

2. How to use this in real systems  
Enable tracing or video for debug builds, capture screenshots on failure, and store artifact paths in job metadata. This usually lives in worker middleware, test harnesses, or audit/reporting services.

```python
await context.tracing.start(screenshots=True, snapshots=True, sources=True)
try:
    await page.goto(job["url"])
    await page.screenshot(path=f"artifacts/{job['id']}.png", full_page=True)
finally:
    await context.tracing.stop(path=f"artifacts/{job['id']}-trace.zip")
```

3. Why does it exist  
Browser failures are visual and timing-sensitive. Without artifacts, postmortems depend on logs alone, which are usually not enough to explain UI failures.

4. What happens if you remove it  
Jobs still fail, but debugging becomes slow and expensive. Teams waste time reproducing issues manually, and intermittent failures remain unresolved longer.

5. When to use vs when not to use  
Use when:
- You need debugging evidence, compliance evidence, or document export
- Failures are intermittent or environment-specific

Avoid when:
- Recording everything would create unnecessary storage and latency cost
- You do not need visual evidence on successful runs

6. Failure patterns & debugging signals  
- Symptom: artifact missing; root cause: wrong close order or path setup; debug: ensure context closes and artifact directories exist.
- Symptom: huge storage growth; root cause: recording every run; debug: enable artifacts selectively.
- Symptom: PDF output differs from screen; root cause: print/media rendering differences; debug: set media mode and compare screenshot vs PDF.

```python
iphone = p.devices["iPhone 13"]
```

**File Upload & Download Handling**

0. Where this fits in the system  
`UI action → browser file boundary → local artifact or remote upload flow`  
`artifact/file event → storage layer → downstream processing`

1. What is this  
This is the browser-to-filesystem integration layer. You study direct file input handling, file chooser events, download events, artifact persistence, and how browser jobs exchange files with the rest of the system.

2. How to use this in real systems  
Use `set_input_files()` for uploads and `expect_download()` around export actions. This usually lives in ingestion/export workers, document-processing pipelines, or enterprise reporting flows.

```python
await page.get_by_label("Upload invoice").set_input_files("invoice.pdf")

```

3. Why does it exist  
Files are not ordinary text fields; they cross a browser and OS boundary. These APIs exist to handle that boundary reliably and without race conditions.

4. What happens if you remove it  
Uploads fail silently or require brittle hacks, downloads are missed, and job outputs never reach storage. Observable issues are hanging exports, missing files, and broken ingestion pipelines.

5. When to use vs when not to use  
Use when:
- The business flow really includes upload or download
- You need end-to-end validation of browser file behavior

Avoid when:
- A direct backend API is the real contract and UI file flow is irrelevant
- You can validate document processing cheaper outside the browser

6. Failure patterns & debugging signals  
- Symptom: no file uploaded; root cause: wrong input target or hidden chooser flow; debug: inspect DOM for real file input or use file chooser event.
- Symptom: download event never fires; root cause: waiter attached after click; debug: register `expect_download()` before triggering action.
- Symptom: file saved but empty/wrong; root cause: server-side export error; debug: inspect response and suggested filename.

**Frames & iframes, Child Frames**

0. Where this fits in the system  
`page loaded → frame boundary detection → frame-scoped interaction`  
`frame-scoped interaction → embedded app or third-party flow`

1. What is this  
Frames are nested documents inside a page. You study iframe boundaries, child frame targeting, `frame_locator()`, and how embedded vendors or legacy apps split the DOM into multiple document scopes.

2. How to use this in real systems  
Use `frame_locator()` when login widgets, payment forms, editors, or third-party embeds live inside iframes. This usually lives in workflow code for integrations with external providers.

```python
payment = page.frame_locator("iframe[name='payment']")
await payment.get_by_label("Card number").fill("4111111111111111")
await payment.get_by_role("button", name="Pay").click()
```

3. Why does it exist  
Embedded systems need isolated documents for security and independent loading. Playwright exposes frame scope because the main page DOM is not enough to reach those elements.

4. What happens if you remove it  
Your selectors search the wrong document, visible elements appear “missing,” and embedded flows fail completely. In production, that looks like broken payments, SSO, or admin widgets.

5. When to use vs when not to use  
Use when:
- The target UI is inside an iframe or child frame
- You integrate with embedded third-party systems

Avoid when:
- The content is in the main document
- You guess frame usage instead of inspecting the page structure

6. Failure patterns & debugging signals  
- Symptom: element clearly visible but not found; root cause: wrong DOM scope; debug: inspect frames and switch to `frame_locator()`.
- Symptom: intermittent frame errors; root cause: iframe loads late; debug: wait for iframe locator or frame content signal.
- Symptom: wrong frame selected; root cause: multiple similar iframes; debug: target by name, URL, or container.

**Shadow DOM Access**

0. Where this fits in the system  
`component-based UI → shadow root boundary → locator traversal`  
`locator traversal → component interaction → app state change`

1. What is this  
Shadow DOM is a web-component encapsulation mechanism. You study how Playwright locators can usually pierce open shadow roots automatically, and where selector strategies like XPath behave differently.

2. How to use this in real systems  
Treat web-component UIs as normal locator targets first and use semantic locators. This usually matters in apps built on custom element design systems or modern component libraries.

```python
await page.get_by_role("button", name="Save settings").click()
await page.get_by_text("Advanced options").click()
```

3. Why does it exist  
Frontend teams use Shadow DOM to isolate component internals and styles. Playwright supports it so automation can work with componentized UIs without coupling to internal markup.

4. What happens if you remove it  
Engineers choose the wrong selector strategy, assume elements are missing, and add brittle workarounds. Observable failures are “element not found” issues in apps that visibly render the component.

5. When to use vs when not to use  
Use when:
- The app uses web components or custom elements
- Normal locators already find open shadow-root content

Avoid when:
- You default to XPath for component internals
- The component uses closed shadow roots you cannot access normally

6. Failure patterns & debugging signals  
- Symptom: CSS/text locator works, XPath fails; root cause: XPath does not pierce shadow roots; debug: switch to locator-based semantic selectors.
- Symptom: component visible but target not found; root cause: closed shadow root or wrong host element; debug: inspect the component structure in devtools.
- Symptom: brittle selectors after component upgrade; root cause: targeting internal implementation; debug: move to role/text/test-id at the component surface.

**Handling Dialogs, Alerts, Confirm, Prompt**

0. Where this fits in the system  
`user action → browser-native dialog → explicit accept/dismiss decision`

1. What is this  
This is the browser-native modal handling layer. You study `alert`, `confirm`, `prompt`, `beforeunload`, and how modal dialogs block the page until automation explicitly resolves them.

2. How to use this in real systems  
Register the dialog handler before the action that triggers it. This usually lives in workflow code for destructive actions, legacy apps, or browser-level confirmation flows.

```python
async def on_dialog(dialog):
    await dialog.accept("approved") if dialog.type == "prompt" else await dialog.accept()

page.on("dialog", on_dialog)
```

4. What happens if you remove it

5. When to use vs when not to use  
Use when:
- The app triggers browser-native alerts, confirms, prompts, or unload dialogs
- Dialog outcome changes the business flow

Avoid when:
- The app uses custom HTML modals instead of native dialogs
- You add a dialog listener but do not resolve the dialog

6. Failure patterns & debugging signals  
- Symptom: click never finishes and job times out; root cause: unresolved dialog; debug: add dialog logging before the triggering action.
- Symptom: prompt accepted with wrong value; root cause: hardcoded input; debug: log dialog type/message and parameterize response.
- Symptom: flaky delete/leave-page flows; root cause: dialog appears only under certain state; debug: capture trace around the trigger.

# MODULE C

**Intercepting requests/responses (`page.route`, `route.continue_()`)**

0. Where this fits in the system  
`page/context request → route handler → continue / abort / fulfill / fetch`  
`route decision → real server or mocked response → frontend state`

1. What is this  
This is Playwright’s request interception layer. It lets your system pause matching network requests and decide whether to send them onward, block them, or replace them. Study subtopics: `page.route()` vs `browser_context.route()`, URL matching, `route.continue_()` in Python, `abort()`, `fulfill()`, `fetch()`, `fallback()`, handler precedence, popup caveats, Service Worker caveats, and the fact that enabling routing disables HTTP cache.

2. How to use this in real systems  
Use this in a worker or browser service before navigation so every request can be governed by policy. Typical uses are blocking heavy assets, mocking unstable APIs, tagging traffic, or modifying responses without touching the app server.

```python
async def install_network_policy(context):
    async def handle(route):
        req = route.request
        if "analytics" in req.url:
            await route.abort()
        elif "/api/report" in req.url:
            upstream = await route.fetch()
            data = await upstream.json()
            data["source"] = "playwright-worker"
            await route.fulfill(response=upstream, json=data)
        else:
            await route.continue_()  # Python uses continue_()
    await context.route("**/*", handle)
```

This usually lives in a browser worker or test harness. In larger systems, `context.route()` is preferred over `page.route()` when popups or multi-page flows are possible.

3. Why does it exist  
Real systems need a control point between the browser and the network. Without interception, you cannot reliably mock dependencies, block wasteful traffic, or make deterministic test and extraction flows when upstream APIs are unstable.

4. What happens if you remove it  
Requests always go straight to the network, so flaky upstream APIs immediately become flaky jobs. You lose the ability to block expensive assets, inject mocks, or debug network-dependent failures. In CI, this usually shows up as slower runs, nondeterministic failures, and dependence on third-party uptime.

5. When to use vs when not to use  
**Use when:**
- You need to block, mock, or modify network traffic
- You need deterministic CI or extraction flows
- You have multi-page flows and want one routing policy for the whole context

**Avoid when:**
- You only need passive observation, not mutation
- You register routes late, after the important requests already fired
- You use `page.route()` for popup-first requests that should be handled at context level

6. Failure patterns & debugging signals  
- Symptom: requests hang until timeout. Likely cause: a route handler matched but never called `continue_()`, `fulfill()`, `abort()`, or `fallback()`. Quick debug: log every matched URL and final route action.
- Symptom: route “does not work” for popup or Service Worker traffic. Likely cause: `page.route()` misses popup first request, or Service Worker intercepted it first. Quick debug: move routing to `browser_context.route()` and set `service_workers="block"` when needed.
- Symptom: app becomes slower after routing enabled. Likely cause: HTTP cache is disabled when routing is on. Quick debug: compare trace timings with and without routing.

7. Importance level  
**Tier 1 (Critical)**

**Capturing XHR / fetch / GraphQL responses**

0. Where this fits in the system  
`UI action or page load → API request/response → response capture → parser/storage`  
`captured payload → normalized records → downstream pipeline`

1. What is this  
This is the API-observation layer for frontend data flows. It lets you capture the structured responses the app already uses, instead of inferring everything from rendered HTML. Study subtopics: `page.on("response")`, `browser_context.on("response")`, `page.expect_response()`, `response.json()`, `response.body()`, request method/resource type filtering, GraphQL endpoint capture, and distinguishing operation types through `request.post_data_json`.

2. How to use this in real systems  
Use response capture in workers that extract business data from dashboards, admin portals, or GraphQL-heavy apps. In larger systems, context-level listeners are useful when jobs open multiple pages or popups.

```python
async def fetch_orders_from_graphql(page):
    async with page.expect_response(
        lambda r: "/graphql" in r.url and r.request.method == "POST"
    ) as resp_info:
        await page.get_by_role("button", name="Load orders").click()

    resp = await resp_info.value
    payload = await resp.json()
    return payload["data"]["orders"]
```

For GraphQL, the response URL alone is often not enough; in real systems you also inspect `resp.request.post_data_json` to identify the `operationName`.

3. Why does it exist  
Modern frontends usually fetch structured data from APIs and only then render DOM. Capturing those responses avoids parsing presentation markup and gives you cleaner, more reliable data closer to the real system boundary.

4. What happens if you remove it  
Your pipeline is forced to scrape the UI even when the data already exists as JSON. That makes extraction slower, more brittle, and more coupled to frontend layout changes. In production, this increases false failures after harmless UI redesigns.

5. When to use vs when not to use  
**Use when:**
- The frontend gets data from XHR, fetch, or GraphQL
- You need structured records, pagination tokens, or hidden metadata
- You want extraction that survives UI redesigns

**Avoid when:**
- The needed information only exists in rendered DOM state
- You cannot uniquely identify the API call you are waiting for
- You assume every `200` response is JSON without checking the endpoint/content type

6. Failure patterns & debugging signals  
- Symptom: wrong response captured. Likely cause: your predicate matches multiple similar requests. Quick debug: log URL, method, status, and GraphQL `operationName`.
- Symptom: JSON parse error. Likely cause: HTML login page, redirect response, or non-JSON body. Quick debug: inspect `response.url`, status, and `await response.body()` length before parsing.
- Symptom: missed response. Likely cause: waiter attached after the triggering click. Quick debug: always attach `expect_response()` before the action.

7. Importance level  
**Tier 1 (Critical)**

**Parsing JSON responses vs scraping DOM**

0. Where this fits in the system  
`captured API payload or rendered page → extraction strategy choice → normalized output`  
`normalized output → storage, ETL, RAG, or downstream services`

1. What is this  
This is the extraction-strategy decision layer. You decide whether to pull data from structured network payloads or from rendered HTML elements. Study subtopics: API-first extraction, DOM scraping, hybrid extraction, schema drift, localization effects, hidden metadata, and when UI state differs from raw backend payloads.

2. How to use this in real systems  
Default to JSON when the frontend already exposes the data through an API call. Fall back to DOM when the value only exists after rendering, formatting, virtualization, or client-side composition. This decision usually lives in your extraction worker or page object layer.

```python
async def extract_products(page):
    try:
        async with page.expect_response("**/api/products*") as api_info:
            await page.goto("https://app.example.com/products")
        data = await (await api_info.value).json()
        return data["items"]                      # API-first path
    except Exception:
        return await page.locator("[data-product-card]").all_inner_texts()  # DOM fallback
```

In larger systems, teams often store both the raw API payload and a small DOM snapshot for audit/debug.

3. Why does it exist  
Not all page data is equally stable or equally truthful at every layer. JSON is usually cleaner and more structured; DOM is closer to what the user actually sees. This distinction exists so systems can optimize for reliability without missing user-visible state.

4. What happens if you remove it  
A one-size-fits-all extractor becomes brittle. If you scrape only DOM, you miss structured metadata and pagination tokens. If you trust only JSON, you can miss final client-side formatting, hidden states, or UI-only computed values.

5. When to use vs when not to use  
**Use when:**
- JSON already contains the business data you need
- DOM is only needed for user-visible formatting or validation
- You want a hybrid strategy for correctness plus resilience

**Avoid when:**
- Scraping DOM just because it is visually obvious
- Assuming API data always matches what the user sees
- Ignoring schema/version drift in upstream JSON

6. Failure patterns & debugging signals  
- Symptom: extractor breaks after redesign. Likely cause: DOM-coupled logic where API data was available. Quick debug: inspect network panel/response events first.
- Symptom: records are structurally correct but visually wrong. Likely cause: API-only extraction missed client-side formatting or filtering. Quick debug: compare API payload to rendered rows.
- Symptom: missing data on infinite-scroll pages. Likely cause: DOM virtualization hides unloaded items. Quick debug: capture the underlying API pagination calls.

7. Importance level  
**Tier 1 (Critical)**

**Observing WebSocket / SSE (events)**

0. Where this fits in the system  
`page/app boot → realtime connection opens → messages/events → app state or monitoring store`  
`stream observation → extraction, replay, or debugging`

1. What is this  
This is the realtime transport observation layer. For WebSockets, Playwright has first-class APIs to observe sockets, frames, and to route/mock them. Study subtopics: `page.expect_websocket()`, `page.on("websocket")`, `WebSocket` frame events, `route_web_socket()`, and `WebSocketRoute.connect_to_server`. Inference from the docs: SSE does not have a dedicated high-level message API in Playwright Python, so teams usually detect it via `request.resource_type == "eventsource"`, response headers like `text/event-stream`, or by validating the DOM/app state it updates.

2. How to use this in real systems  
Use this in dashboard monitors, chat agents, live-feed collectors, or apps that never expose their final state through plain XHR. This usually lives in a specialized browser worker or debug harness.

```python
async def watch_live_feed(page):
    async with page.expect_websocket() as ws_info:
        await page.goto("https://app.example.com/live")

    ws = await ws_info.value
    ws.on("framereceived", lambda msg: print("recv:", msg))
    page.on("request", lambda req: print("SSE:", req.url) if req.resource_type == "eventsource" else None)
```

For interception or mocking, register `route_web_socket()` before page creation/navigation.

3. Why does it exist  
Many modern systems stream updates instead of polling. Without stream observation, the browser sees changing state but your automation has no reliable record of the events that caused it.

4. What happens if you remove it  
Live dashboards appear “random” because state changes without visible API calls you are capturing. Jobs miss transient messages, and flaky realtime issues become extremely hard to reproduce.

5. When to use vs when not to use  
**Use when:**
- The app depends on WebSocket or SSE streams
- Data changes continuously after initial page load
- You need to validate or debug live event flows

**Avoid when:**
- The app is purely request/response driven
- You only care about final DOM state and not the stream itself
- You try to parse SSE like a normal completed JSON response

6. Failure patterns & debugging signals  
- Symptom: no WebSocket events captured. Likely cause: listener or route registered after socket creation. Quick debug: attach `expect_websocket()` before navigation.
- Symptom: SSE connection seen but no extracted data. Likely cause: SSE is long-lived and not exposed as a single JSON body. Quick debug: validate `eventsource` request presence and inspect DOM/state changes instead of waiting for full response body.
- Symptom: routed WebSocket stops forwarding. Likely cause: calling `on_message()` changes default forwarding behavior. Quick debug: explicitly forward messages with `send()` or `connect_to_server`.

**Tier 2 (Important)**

**Saving assets (images, PDFs)**

0. Where this fits in the system  
`network response or browser download → binary capture → local/object storage`  
`stored asset → OCR, RAG, audit trail, user delivery`

1. What is this  
This is the binary artifact extraction layer. It covers saving files the page loads or downloads, rather than only text or JSON. Study subtopics: saving binary bodies with `response.body()`, handling attachment downloads with `expect_download()`, file naming, content-type checks, temp download lifetime, and when to use response capture vs download APIs.

2. How to use this in real systems  
Use this in invoice ingestion, image archiving, evidence capture, or RAG pipelines. This typically lives in a browser worker that persists bytes to local staging or object storage before the context closes.

```python
from pathlib import Path

async def save_invoice_pdf(page, job_id):
    async with page.expect_response(lambda r: "/invoices/" in r.url and r.status == 200) as info:
        await page.get_by_role("link", name="Invoice PDF").click()

    resp = await info.value
    Path(f"artifacts/{job_id}.pdf").write_bytes(await resp.body())
```

If the server sends the file as an attachment download, use `expect_download()` instead and save it before closing the context.

3. Why does it exist  
Real systems often care about the actual file, not just the page text that links to it. This layer exists because binary assets cross a different boundary than DOM extraction and need explicit persistence.

4. What happens if you remove it  
You can read metadata about files but not capture the actual artifact. OCR, document ingestion, audit storage, and downstream file processing all fail or become manual.

5. When to use vs when not to use  
**Use when:**
- The business output is an image, PDF, or other binary artifact
- You need evidence files for audit or downstream processing
- The app exposes critical data as downloadable documents

**Avoid when:**
- You only need metadata, not the file bytes
- You leave downloads in temp storage and close the context before saving
- You assume every PDF/image comes through the download API rather than normal responses

6. Failure patterns & debugging signals  
- Symptom: empty or wrong file. Likely cause: saved a login/HTML error page instead of the binary. Quick debug: verify URL, status, and content type before writing bytes.
- Symptom: file disappears after the run. Likely cause: downloaded files live in temp storage and are deleted when the producing context closes. Quick debug: call `save_as()` before cleanup or set a downloads path.
- Symptom: file capture never triggers. Likely cause: used `expect_download()` for a normal inline response, or vice versa. Quick debug: inspect whether the browser treated the asset as a page response or an attachment.

**Headless vs headful tradeoffs**

0. Where this fits in the system  
`launch policy → browser mode selection → execution speed/visibility/debuggability`  
`mode choice → worker cost, CI reliability, human debugging`

1. What is this  
This is the runtime operating-mode choice for the browser. Headless runs without a visible UI and is the default; headful opens the browser window. Study subtopics: `headless=True/False`, debug runs, `slow_mo`, Inspector/PWDEBUG, CI usage, and operational differences between production runs and debugging runs.

2. How to use this in real systems  
Run production workers headless for speed and scalability. Re-run failed jobs in headful mode with `slow_mo` or `PWDEBUG` when a human needs to inspect what the browser is doing. This typically lives in launch configuration or retry policy.

```python
async def launch_browser(p, debug=False):
    return await p.chromium.launch(
        headless=not debug,
        slow_mo=150 if debug else 0,
    )
```

A common system pattern is: first attempt headless in the worker pool, second attempt headful in a debug queue.

3. Why does it exist  
Production systems need efficient non-visual automation, but humans need visibility during debugging. One mode optimizes scale; the other optimizes understanding.

4. What happens if you remove it  
If everything is headless, hard UI bugs are much slower to diagnose. If everything is headful, CI and workers consume more resources, run slower, and are harder to operate at scale.

5. When to use vs when not to use  
**Use when:**
- Headless for CI, batch workers, and scalable automation
- Headful for live debugging, flaky UI investigation, and manual analysis

**Avoid when:**
- Running all production jobs headful without a real need
- Treating headful as a reliability fix instead of a debugging aid
- Ignoring that launch mode can change timing and diagnostics

6. Failure patterns & debugging signals  
- Symptom: job only fails in headless mode. Likely cause: timing/render/debug-visibility differences or site-specific behavior. Quick debug: rerun headful with trace, screenshots, and `slow_mo`.
- Symptom: worker capacity is poor. Likely cause: headful mode used in production. Quick debug: compare CPU/memory per job and move debug runs to a separate path.
- Symptom: impossible to understand a flaky UI issue from logs. Likely cause: no visible/debug path. Quick debug: enable headful + Inspector + trace capture.

**HAR capture & replay**

0. Where this fits in the system  
`live browser session → HAR recording → reusable network snapshot`  
`replay context → HAR-served requests → deterministic frontend run`

1. What is this  
This is the network recording and replay layer. HAR stores request/response traffic so later runs can replay it instead of hitting the live network. Study subtopics: `record_har_path`, `record_har_mode`, `record_har_content`, `route_from_har()`, `not_found`, `update`, context-vs-page scope, and Service Worker caveats.

2. How to use this in real systems  
Record a known-good session in staging or dev, then replay it in CI or offline extraction tests. This usually lives in test infrastructure, reproducibility tooling, or local debugging flows.

```python
# record
context = await browser.new_context(record_har_path="session.har", record_har_mode="minimal")
page = await context.new_page()
await page.goto("https://app.example.com")
await context.close()  # HAR is written on close

# replay
context = await browser.new_context(service_workers="block")
await context.route_from_har("session.har", not_found="fallback")
```

Use context-level replay when the app opens multiple pages or popups.

3. Why does it exist  
Live network dependencies make tests and data flows slow, flaky, and environment-dependent. HAR replay exists to make network behavior reproducible without standing up every upstream dependency.

4. What happens if you remove it  
Your system depends on live APIs for every run, so CI becomes slower and more fragile. Reproducing old bugs becomes harder because the backend state and traffic have changed.

5. When to use vs when not to use  
**Use when:**
- You want deterministic frontend runs
- External APIs are slow, flaky, or costly
- You need reproducible debugging for network-dependent issues

**Avoid when:**
- You need to validate fresh live data on every run
- The app behavior changes too often for recorded traffic to stay valid
- You forget Service Worker and scope caveats when replaying

6. Failure patterns & debugging signals  
- Symptom: HAR file never appears. Likely cause: context was not closed, so recording was never flushed. Quick debug: ensure `context.close()` runs even on failure.
- Symptom: requests still hit the live network unexpectedly. Likely cause: `not_found="fallback"` plus missing HAR entries, URL mismatch, or Service Worker interference. Quick debug: log unmatched URLs and use `service_workers="block"` when replaying.
- Symptom: replayed app state is stale or wrong. Likely cause: HAR no longer matches current frontend/backend contract. Quick debug: re-record HAR and compare changed endpoints.
